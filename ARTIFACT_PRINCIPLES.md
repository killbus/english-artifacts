# Artifact Principles

This document is the product constitution for PDF-first artifacts.

## 1. A PDF needs a job

Do not make a PDF merely because PDF is convenient.

The artifact must have a clear user job that is better served by the artifact's persistence, structure, portability, or repeatability.

## 2. The PDF is not a disguised course

Information may support the artifact, but teaching content is not automatically product value.

## 3. Guide behavior, not attendance

Do not default to streaks, daily checkboxes, completion percentages, or challenge mechanics.

The user should be guided to do something useful, not merely to record that they showed up.

## 4. Important user input should matter later

When an artifact uses an Echo model, meaningful input should have a future return path.

## 5. Static does not mean one-pass

A static file can still create a multi-stage experience through cross-page references, personal IDs, prior-version comparison, reuse, and visible accumulation.

## 6. Time is optional

Dates may support the artifact, but date progression must not be the product's default structure.

## 7. Completion is not value

A finished PDF is not necessarily a successful PDF.

Measure whether the artifact changed or supported behavior.

## 8. Do not optimize for page count

A page exists because it performs a user job, not because the product needs to look substantial.

## 9. Personal accumulation is a feature

When appropriate, the user's own history should become a growing part of the artifact.

## 10. Protect the distinction between product and implementation

Layout, code, and reusable components serve product behavior. They do not define it.

## 11. Avoid fake personalization

If the artifact cannot meaningfully use a user's prior input, do not call it an adaptive or personalized system.

## 12. One experiment should isolate one important question

Do not change audience, promise, format, pricing, and interaction model simultaneously unless the purpose is exploratory rather than diagnostic.
